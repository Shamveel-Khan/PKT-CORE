`validate.py` cannot report a false pass over duplicates: a count is only printed
alongside its distinct count, and every audit finding becomes a failure. A copy
of this artefact with a single AAA client duplicated fails with
`duplicate-aaa-client: AAA client … occurs 2 times (140 aaa_clients counted, only
139 distinct)`.

### What each check actually proves

| Check | Method | What it proves |
| --- | --- | --- |
| **byte-exact round-trip** | `encode(decode(f)) == f` on the emitted container | the file is a well-formed member of the PT container family; the codec is lossless on it (the toolkit demonstrates this on 1,058 real containers) |
| **XML legality** | scans every character for C0 control bytes outside `\t\n\r` | the document is valid XML 1.0 — this is why the generators avoid Cisco's `banner … ^C` idiom, whose `^C` is a raw `0x03` |
| **device power** | every `<DEVICE><ENGINE><POWER>` must be `true` unless the device name is on the explicit staged-off allow-list (`STAGED_OFF`) | no device inherits a stale harvested power state — the defect that shipped all ten `3650-24PS` core/aggregation switches off (template harvested from a save where that switch was off). `<PORT><POWER>` is a different field and is deliberately not checked here |
| **port-name evidence** | every `(model, port)` pair in every `<LINK>` is looked up in `build/port_model.json` | PT will resolve each cable to a real interface — an unattested port name is the most likely cause of a silently dead link |
| **double-booked ports** | no `(device, port)` appears in two `<LINK>`s | no accidental cable collision |
| **config presence** | all 143 IOS/ASA devices have a non-empty `RUNNINGCONFIG` | nothing was left unconfigured |
| **service injection** | counts DNS `RESOURCE-RECORD`s, DHCP `POOL`s and `ACS_CLIENT`s | the service configuration really landed in the device model, not just in a comment |
| **address uniqueness** | every `<PORT><IP>` value counted | no duplicate host addresses survive from the harvested device templates |

### Evidence base behind the port-name check

`tools/build_port_model.py` builds the allowed port set for each model from five
tiers, all recorded per port in `build/port_model.json`:

| Tier | Source | Example fact it establishes |
| --- | --- | --- |
| `sample-link` | Cisco's own PT 9.0.1 sample labs (299 files) | `IR1101` exposes `GigabitEthernet0/0/0`; `IE-9320` exposes `GigabitEthernet1/0/1…24`; `Cell-Tower` exposes `Coaxial0/0` |
| `corpus-link` | 1,058-file community reference corpus (952 fetched, hash-verified) | `2911` with an HWIC-2T exposes `Serial0/0/0…Serial0/3/1`; `3560-24PS` exposes `FastEthernet0/1…24` plus `GigabitEthernet0/1,0/2` |
| `sample-ios` | interface names inside Cisco-shipped running-configs | `IR1101` exposes `FastEthernet0/0/1…0/0/4` (its built-in 4-port switch) |
| `corpus-ios` | interface names inside community running-configs | `5505` exposes `Ethernet0/0…0/7` and routes on `Vlan1`/`Vlan2` |
| `template` / `module` | the model's port inventory in `device_templates.json` | used **only** to extend an already-attested family across its numeric range — never to invent a family |

A port name is accepted only if its media family exists on that model at all,
which discards mis-attributed names the corpus contains (for example
`FastEthernet0/1` recorded against a `3650-24PS`, which has no Fast Ethernet
ports).

### Three defects this verification found, and their fixes

Opening the file in the real simulator was worth doing — it caught three things
that no static check would have:

1. **Serial bearers had no addressing.** `router_config()` only emits an
   `interface` block for interfaces registered as routed ports, and the serial
   bearers never were — so the aircraft and concentrator serial interfaces had
   no IP address and no `no shutdown`, and the datalinks never came up. Fixed by
   giving every serial bearer its own `/30` from the backbone pool
   (`JASDF.slink()`), which also brought them into OSPF.

2. **Access-point ports ship powered off.** The harvested `AccessPoint-PT`
   template carries `<POWER>false</POWER>` on its ports, so every base and
   airborne WLAN link rendered down. Fixed generally in
   `JASDF.power_cabled_ports()`: a cabled port on a device we placed is by
   definition powered.

3. **The airborne LAN was not a real L2 domain.** The mission router had a
   single untagged address on `GigabitEthernet0/0` while the onboard switch put
   the mission computer, access point and console in different VLANs — so they
   were isolated. Fixed by making each airframe a proper 802.1Q site: the router
   does router-on-a-stick with subinterfaces on VLANs 10/20/40/50, matching the
   site pattern used everywhere else.

### Device-level power — `power_all_devices()`

A later static audit (`docs/POWER_INVESTIGATION.md` in the toolkit) found the
device-level sibling of item 2: `lab_api.add_device()` only ever wrote
`<POWER>false</POWER>`, never `true`, so every device inherited
`<ENGINE><POWER>` from its harvested model template. Exactly one of the 137
templates (`MultiLayerSwitch`/`3650-24PS`) was harvested from a save where that
switch was off, which shipped **all ten core/aggregation switches**
(`JADGE-BB-SW-01/02`, `REG-HUB-NORTH/CENTRAL/WEST/SW`, `DATALINK-AGG-01/02`,
`JADGE-DC-CORE-01/02`) powered down — 76 of 326 links (23.3 %) came up dark.

Fixed at three levels:

* `lab_api.add_device()` now writes `<ENGINE><POWER>` explicitly in both
  directions (created at its canonical slot, child index 2, when missing);
* harvesting normalises device power to `true` and records the donor state;
* `JASDF.power_all_devices()` (run in `main()` beside `power_cabled_ports()`)
  forces `<ENGINE><POWER>true</POWER>` on every placed device, keeping
  `power=False` only for gear explicitly listed in `JASDF.STAGED_OFF`
  (empty for this lab).

The delivered artefact was repaired in place (only the ten `<ENGINE><POWER>`
texts changed; `<PORT><POWER>` untouched) and `validate.py` now **fails** any
device left with `POWER` ∈ {`false`, absent} unless it is staged off.

### A note on amber link lights

Packet Tracer runs spanning-tree convergence after loading any file containing
switches, so some access ports show **amber** link lights for the first ~30
seconds. Cisco documents this:

> "The amber link light indicates that the switch port is not in STP forwarding
> state. STP takes over 30 seconds to put a port into forwarding state if there
> are no loops." — *Packet Tracer Help, faqTroubleShoot.htm*

> "When first loading files with switches … the Spanning Tree Protocol will go
> through the different states on the ports before putting them in forwarding
> state, indicated by an amber light. If this causes an annoying delay, toggling
> between Realtime and Simulation mode 3 or 4 times will decrease the delay."
> — *Packet Tracer Help, connectionsLinks.htm*

This was confirmed experimentally three ways: the same switch configuration
produces green ports in an isolated probe (`tools/stp_probe.py`); toggling
Realtime/Simulation clears the amber state on the full lab; and the amber is
transient, not persistent. It is not a defect in the model.

Both states were captured from this lab: `packet_tracer_shipped_load.png` still
shows two amber ports at the moment of load, and `packet_tracer_verified.png`
(above) shows the same lab fully converged.

With 290 devices and 31 switches, PT's convergence on this lab can take longer
than the ~30 s a small lab needs; on the capture above it had not finished after
75 s, whereas an earlier run of the same file converged fully. Reloading the
file or toggling simulation modes clears it.

### A note on red serial cables

Packet Tracer draws **serial cables in red** regardless of link state. A minimal
two-router probe (`tools/serial_probe.py`) confirms this: a single 2911↔2911
serial link shows a red cable with **green** indicators at both ends. The
airborne datalink bearers in the model behave identically.

## 3. What was *not* verified

Stated plainly, so the evidence is not overread:

* **No end-to-end traffic was generated.** Nothing here proves a ping from a
  radar site to the JADGE data centre succeeds. What is proven is that the
  topology, addressing, interface configuration and link state are all correct
  as far as Packet Tracer's loader is concerned. Ping/OSPF-adjacency testing
  requires interactive use of Packet Tracer.
* **Only the airborne tier was visually inspected in detail.** The screenshot
  above shows the AEW&C segment; the radar, air-base, CRC and data-centre tiers
  render (they are present in the file and validated structurally) but were not
  individually photographed.
* **Packet Tracer's IOS is a subset of Cisco IOS.** A command that PT does not
  implement is ignored or errors in the CLI tab without invalidating the file.
  Everything emitted is a standard CCNA/CCNP-level construct or is attested in
  the reference corpus, but PT's acceptance of each individual command was not
  exhaustively tested.
* **The `.pkt` container codec is verified byte-exact; Packet Tracer's own
  acceptance is verified only for this file and version (9.0.1.0858).** Earlier
  PT releases use a different (legacy) container family and were not tested
  here.

## 4. Reproducing the verification

```console
$ python build_jasdf_aewc.py --profile enterprise --out out/JASDF_AEWC_JADGE.pkt
$ python validate.py out/JASDF_AEWC_JADGE.pkt

# Open it in a real Packet Tracer (headless example)
$ Xvfb :98 -screen 0 1920x1200x24 &
$ DISPLAY=:98 packettracer out/JASDF_AEWC_JADGE.pkt &
#   then, after ~30 s, toggle Realtime <-> Simulation 4x to clear STP transients
```
